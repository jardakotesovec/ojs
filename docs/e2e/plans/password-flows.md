# Password flows

- **Area:** 5. Users, roles & access
- **Placement:** lib/pkp
- **Budget:** 5 tests
- **Absorbs (rework):** lib/pkp/playwright/tests/mailpit.spec.js — its password-reset test only (request → mail arrival), DONE: that test was removed from mailpit.spec.js and reworked into row 1's full reset round-trip (throwaway user instead of dbarnes). The other two mailpit.spec.js tests (clearAll harness, Mail::fake leak check) stay in that file for the `test-infrastructure` plan, not here. Split note: mailpit.spec.js now backs 2 tests (both test-infrastructure), password-flows.spec.js backs the 5 rows below. While splitting, the leak-check test had to be made parallel-safe: its `clearAll()` + global `messageCount() === 0` assertion failed whenever any concurrent test sent mail (observed: row 1's own reset mail landed between the clear and the count under `--workers=2`); it now asserts zero tag-marked mail across the fixture's recipient cast, bounded by a positive control (principle 8). The global-count form can return when test-infrastructure relocates that spec to `tests/serial/`.
- **Scenario needs:** journal scenario `users[]` with `password` (throwaway users — password mutations must never touch the 16 shared seeded users, whose cached auth state would break parallel tests) and `mustChangePassword: true` (verified: context schema `users[]` property + `UserAssignmentProcessor.php:97`) for the forced-change row. Mailpit fixture (`pkpMail`) for reset mail; tests assert per-recipient with unique-tag emails and never call `clearAll()` (principle 8 — shared inbox; the only `clearAll()` lives in the serial `test-infrastructure` spec); every negative assertion ("no mail sent") is paired with a positive control message that bounds the wait.
- **Implementation notes:**
  - The PASSWORD_RESET_CONFIRM body carries the reset URL as a RAW string ("Reset my password: http://…"), not an `<a>` anchor — `pkpMail.extractLink` does not apply; the spec regexes the URL out (`extractResetUrl`) and decodes `&amp;` defensively.
  - Invalid/expired hash renders the frontend error page (`user.login.lostPassword.invalidHash`) with a back link to `lostPassword`; only an UNKNOWN username in the link 302s straight to `lostPassword`. Row 2 asserts both shapes.
  - Profile Password tab is a legacy AjaxFormHandler form: validation failures re-render the form with fields cleared and surface errors only via the in-place notification `#changePasswordFormNotification` (no inline field error for `oldPassword` — it has no fbv sub-label to host one).
  - `FormValidatorPassword` reports only the FIRST failing rule (required → confirmed → min), so row 5 provokes length and mismatch errors with separate submissions.
  - Site `minPasswordLength` is the installer default 6 (`PKPInstall::MIN_PASSWORD_LENGTH`); scratch journals inherit it, no site mutation needed.
- **Round 2 / out of scope:**
  - Captcha / rate limiting on the lost-password form (deferred in inventory).
  - `email.require_validation` interaction with reset flows.
  - Site-admin forced password invalidation policies (no UI surface found; do not invent).
